# 注释检查技能

## 检查目标

对 `src/` 目录下所有 `.ts` 和 `.tsx` 文件执行三项检查：

1. **注释覆盖率** — 每个函数/核心逻辑是否有注释，比例是否达标（约 3:7，即 10 行中 3 行注释 + 7 行代码）
2. **注释准确性** — 注释内容和代码实际行为是否一致
3. **注释可读性** — 注释语言是否从编程小白角度出发，避免技术行话

## 执行流程

严格按照以下顺序执行：

### 第 1 步：收集文件

用 Glob 搜索 `src/**/*.ts` 和 `src/**/*.tsx`，排除 `.test.ts` 测试文件（测试文件不需要注释检查）。

```bash
# 用 Glob 工具搜索，pattern 为 src/**/*.{ts,tsx}，然后手动排除 .test.ts
```

### 第 2 步：逐文件检查

对每个文件，逐项检查。在分析过程中记录以下信息到内存中：

#### 检查项 A — 注释覆盖率

对文件中的每个函数（包括 export 函数、内部辅助函数、React 组件），判断：

1. 函数是否有顶部注释（说明这个函数是干什么的）？
2. 函数内部的核心步骤是否有行内注释？
3. 整体注释行数占文件总行数的比例是否 ≥ 20%？（放宽标准，大概 2:8 即达标）

**判定规则**：
- 导出函数/组件：必须要有顶部注释，缺少则记为一个 🔴 严重问题
- 内部函数/辅助函数：建议有注释，缺少则记为一个 🟡 轻微问题
- 核心逻辑行（如复杂计算、状态判断、数据处理）：建议有行内注释，缺少则记为一个 🟡 轻微问题
- 整体注释比例 < 10%：记为一个 🔴 严重问题
- 整体注释比例 10%~20%：记为一个 🟡 轻微问题

#### 检查项 B — 注释准确性

对每条注释，核对其描述是否和代码实际做的事一致：

1. 注释中描述的参数名、返回值类型是否和代码一致？
2. 注释描述的功能逻辑是否和代码实现匹配？
3. 代码重构后注释是否忘记更新？（比如注释说"返回数组"但代码已改为返回对象）

**判定规则**：
- 注释和代码明显矛盾：🔴 严重问题
- 注释描述模糊但能看出意图：🟡 轻微问题

#### 检查项 C — 注释可读性（小白视角）

对每条注释，判断是否一个编程新手能看懂：

1. 是否包含了不必要的英文术语？（如 "SQLite WASM"、"localStorage"、"Promise"、"async/await"）
2. 是否用了缩写而未解释？
3. 描述是否通俗？比如 "将数据序列化后持久化到本地存储" 应该写成 "把数据转成字符串，保存到浏览器本地"

**判定规则**：
- 注释中含有至少 2 个技术术语且未解释：🔴 严重问题
- 注释使用了专业术语但上下文能猜出意思：🟡 轻微问题

### 第 3 步：修复问题

对于发现的每个问题，**自动修复**（方案 B）：

- **缺少注释** → 根据函数名和代码逻辑，补写注释（用中文、小白视角）
- **注释不准确** → 根据代码实际行为，修正注释内容
- **注释可读性差** → 改写注释，替换术语为通俗表达

修复时直接编辑文件，完成后记录修改了什么。

### 第 4 步：生成报告

按以下格式输出报告：

```
📋 注释检查报告

📁 检查范围: src/ 下 X 个文件（.ts / .tsx）

🔴 严重问题: Y 个（已修复）
🟡 轻微问题: Z 个（已修复）

---

📄 src/data/categories.ts
  ✅ 注释覆盖率: 25%（达标）
  🔴 已修复: getSubcategories() 缺少函数注释 → 已添加
  🟡 已修复: "SQLite WASM" 术语 → 已改为通俗解释

📄 src/components/AddExpense.tsx
  ...
```

## 注意事项

- **只检查 `.ts` 和 `.tsx` 文件**，不检查 `.test.ts`、`.d.ts`、配置文件
- **修复时保持代码逻辑不变**，只改注释
- **不要删除任何现有注释**，只在不够时补充、不准确时修正
- **注释语言全部用中文**
- 每改完一个文件，把改动的内容简单告诉用户
